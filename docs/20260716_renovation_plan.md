# Lumina 对话体验改造计划

> 基于 `docs/20260716_log_analysis.md` 的分析结论，制定本改造计划。目标是通过系统性的工程改造，解决「用户信息记不住」「平台乱窜」「对话连续性丢失」「任意入口被当作新对话」等核心问题。

---

## 一、改造目标

| 目标编号 | 目标 | 衡量标准 |
|---|---|---|
| G1 | 建立可复用的多轮会话机制 | 同一会话连续 5 轮 `conversation_id` 一致，`history_len` 逐轮递增 |
| G2 | 消除平台乱窜 | 用户已声明平台后，后续 90% 的工具调用平台与声明一致 |
| G3 | 恢复对话连续性 | 「那么图文的又咋做」「接上一个问题」等省略表达可被正确承接 |
| G4 | 确保任意入口 conversation_id 复用 | 刷新页面或从任意入口重新进入后，`conversation_id` 一致，不重新开场 |
| G5 | 提升长对话稳定性 | 10 轮以上对话仍能准确回忆平台、赛道、人设等关键事实 |

---

## 二、改造原则

1. **先基建后体验**：先解决会话管理和平台画像，再优化 LLM 理解和工具策略。
2. **最小侵入**：尽量复用现有 `planner` path 和工具，不推翻已有架构。
3. **数据驱动**：每次改造都配套日志字段和验收指标，便于验证效果。
4. **分阶段灰度**：按 P0 → P1 → P2 阶段推进，每阶段完成后用回归用例验证。

---

## 三、改造范围

| 层级 | 涉及模块 | 主要改造点 |
|---|---|---|
| 前端 | 对话页面、路由切换、入口恢复 | `conversation_id` 持久化（localStorage/sessionStorage）、刷新/切换后恢复会话 |
| 后端 | 会话服务、消息存储、画像服务 | 会话历史查询、历史消息拼接、用户画像维护、平台回填 |
| LLM/planner | system prompt、工具参数生成 | 上下文提示、平台一致性校验、指代消解、会话摘要 |
| 工具 | `lumina_recommend_topics`、`lumina_positioning_matrix` 等 | 平台参数读取顺序、多工具平台统一 |
| 可观测 | 日志、监控 | 新增字段、回归测试用例、指标看板 |

## 四、分阶段实施计划

### 阶段一：会话记忆基建（P0，第 1-2 周）

#### 4.1.1 目标
让后端具备根据 `conversation_id` 查询历史消息的能力，并拼入 LLM prompt；前端确保同一对话复用 `conversation_id`。

#### 4.1.2 任务清单

| 任务编号 | 任务 | 负责人 | 输出物 | 验收标准 |
|---|---|---|---|---|
| P0-1 | 建立会话消息存储表 | 后端 | 数据库表/Redis 结构 | 支持按 `conversation_id` 分页查询消息 |
| P0-2 | 改造请求入口：根据传入 `conversation_id` 查询历史 | 后端 | API 改动 | 连续请求返回的 `history_len` 递增 |
| P0-3 | 将历史消息按规则拼入 LLM prompt | 后端/LLM | prompt 模板 | 模型能看到前 N 轮用户和助手消息 |
| P0-4 | 前端持久化 `conversation_id` 并复用 | 前端 | localStorage/sessionStorage 逻辑 | 刷新页面、切换路由或从任意入口进入后 `conversation_id` 不变 |
| P0-5 | 定义会话新建/恢复策略 | 产品/后端 | 策略文档 | 明确何时新建、何时复用 |

#### 4.1.3 关键设计

- **消息存储结构**：
  ```json
  {
    "conversation_id": "uuid",
    "user_id": "15201271737",
    "messages": [
      {"role": "user", "content": "...", "ts": "..."},
      {"role": "assistant", "content": "...", "ts": "...", "tool_calls": [...]}
    ],
    "created_at": "...",
    "updated_at": "..."
  }
  ```

- **历史拼接策略**：
  - 默认取最近 10 轮（20 条）消息。
  - 若超长，优先保留最近 5 轮 + 会话摘要（阶段三实现）。
  - 当前请求单独作为最后一条 user 消息，不参与历史计数。

- **会话生命周期**：
  - 用户首次进入时，前端生成新的 `conversation_id` 并保存。
  - 用户主动点击「新建对话」时，清空并生成新 ID。
  - 刷新页面、切换路由或从任意入口（如解决方案、账号诊断等）重新进入时，前端先从本地存储读取已有 `conversation_id` 并复用。
  - 会话 30 分钟无交互后，再次进入默认恢复最近活跃会话（或提示选择）。

#### 4.1.4 回归用例

- 用例 R1：用户连续发送 3 条消息，验证 `conversation_id` 相同，`history_len` 依次为 0、2、4。
- 用例 R2：刷新页面后发送消息，验证 `conversation_id` 与刷新前一致。
- 用例 R3：复现第 28→29 条场景，验证「那么图文的又咋做」能承接视频脚本主题。

### 阶段二：平台与用户画像持久化（P0，第 2-3 周）

#### 4.2.1 目标
将用户声明的平台、赛道、目标人群等关键信息持久化，工具调用优先读取画像，而非让 LLM 每次重新推断。

#### 4.2.2 任务清单

| 任务编号 | 任务 | 负责人 | 输出物 | 验收标准 |
|---|---|---|---|---|
| P0-7 | 设计会话级画像表 | 后端 | 表结构 | 包含 platform、niche、target_audience、content_style、goals 等字段 |
| P0-8 | 实现平台识别与提取逻辑 | 后端/LLM | 提取函数 | 从用户消息或工具调用中识别平台，准确率 ≥ 90% |
| P0-9 | 实现画像更新策略 | 后端 | 更新逻辑 | 用户声明或工具调用后，画像字段被更新 |
| P0-10 | 工具调用平台参数读取顺序改造 | 后端/LLM | 工具参数生成逻辑 | 优先使用画像 platform，其次当前消息，最后 LLM 推断 |
| P0-11 | 顶层 `platform` 字段回填 | 后端 | 请求日志 | 日志中 `platform` 字段不再为空 |
| P0-12 | 平台变更处理 | 后端 | 策略文档 | 用户明确切换平台时，更新画像并提示 |

#### 4.2.3 关键设计

- **画像字段**：
  ```json
  {
    "conversation_id": "uuid",
    "user_id": "...",
    "platform": "shipinhao",
    "platform_cn": "视频号",
    "niche": "健康养生",
    "target_audience": "35-65岁中老年",
    "content_style": "干货型/跟练型",
    "goals": ["涨粉", "打造IP"],
    "updated_at": "..."
  }
  ```

- **平台识别规则**：
  - 中文识别：「视频号」「小红书」「抖音」「B站」「快手」等。
  - 英文标识：`shipinhao`、`xiaohongshu`、`douyin`、`bilibili`、`kuaishou`。
  - 优先级：用户明确声明 > 工具调用中已使用的平台 > 历史画像 > LLM 推断。

- **平台参数生成规则**：
  - 如果画像中存在 platform，且用户当前消息未明确切换到其他平台，则所有工具调用统一使用该 platform。
  - 如果用户消息明确说「对比小红书/抖音」，允许多平台调用。
  - 如果画像为空且当前消息未指定平台，LLM 推断后写入画像，供后续使用。

#### 4.2.4 回归用例

- 用例 R4：用户说「我要做视频号养生账号」，后续发送「怎么涨粉」不带平台词，验证工具调用平台为 `shipinhao/视频号`。
- 用例 R5：复现第 14 条「怎么打造养生账号 ip」，验证工具调用平台为视频号而非小红书。
- 用例 R6：复现第 7 条「刚开通账号，喜欢养生运动」，验证同一请求内工具平台一致（不应同时出现 xiaohongshu 和 douyin）。

### 阶段三：工具层与平台一致性校验（P1，第 3-4 周）

#### 4.3.1 目标
统一一次请求内的工具平台参数，确保同一次请求中所有工具调用使用一致的平台。

#### 4.3.2 任务清单

| 任务编号 | 任务 | 负责人 | 输出物 | 验收标准 |
|---|---|---|---|---|
| P1-1 | 工具调用前增加平台归一校验 | 后端/LLM | 校验函数 | 同一次请求中所有工具 platform 一致（除非用户明确对比） |
| P1-2 | 多平台对比需求识别 | 后端/LLM | 识别逻辑 | 用户明确说「对比」时，允许同时调用多个平台 |

#### 4.3.3 关键设计

- **平台归一校验**：
  - 在 planner 生成工具参数后、调用工具前，遍历所有工具参数。
  - 若存在多个不同 platform，则按优先级统一：画像平台 > 当前消息中的平台 > 出现次数最多的平台。
  - 若用户明确表达对比（如「对比小红书/抖音」），跳过校验。

- **校验示例**：
  - 第 7 条原本同时调用 `xiaohongshu` 和 `douyin`，校验后应统一为画像中的视频号（或用户当前明确指定的平台）。
  - 用户说「对比小红书/抖音」时，保留两个平台调用。

#### 4.3.4 回归用例

- 用例 R7：复现第 7 条场景，验证一次请求内工具平台统一为视频号。
- 用例 R8：用户说「对比小红书/抖音」，验证允许同时调用两个平台。

### 阶段四：长对话稳定性与摘要（P1，第 4-6 周）

#### 4.4.1 目标
解决历史消息过长导致关键信息被淹没的问题，提升 10 轮以上长对话的稳定性。

#### 4.4.2 任务清单

| 任务编号 | 任务 | 负责人 | 输出物 | 验收标准 |
|---|---|---|---|---|
| P1-3 | 设计会话摘要机制 | 后端/LLM | 摘要策略 | 每 N 轮或 token 超限时生成摘要 |
| P1-4 | 实现关键信息提取 | 后端/LLM | 提取函数 | 从对话中提取 platform、niche、audience、goals 并更新画像 |
| P1-5 | 改造历史拼接策略 | 后端 | prompt 模板 | 长对话时优先使用摘要 + 最近轮次 |
| P1-6 | 画像回写到 system prompt | 后端/LLM | system prompt | 每轮请求都携带用户画像 |

#### 4.4.3 关键设计

- **摘要触发条件**：
  - 每 6 轮生成一次摘要。
  - 或当历史消息 token 数超过阈值（如 3000 tokens）时触发。

- **摘要内容**：
  ```markdown
  用户已声明：平台=视频号，赛道=健康养生，目标人群=中老年，目标=打造养生IP/涨粉。
  已讨论话题：账号定位、养生运动方向、视频脚本生成。
  用户偏好：喜欢运动类养生内容，不喜欢专家型人设，倾向于轻养生实践派。
  ```

- **历史拼接策略**：
  - 短对话（≤6 轮）：完整拼接所有消息。
  - 长对话（>6 轮）：拼接「摘要 + 最近 3 轮完整消息 + 当前请求」。

- **画像回写**：
  - 在 system prompt 中固定追加：
    ```
    当前用户画像：平台=视频号，赛道=健康养生，目标人群=中老年，人设=轻养生实践派。
    请优先使用画像中的信息，不要推断为其他平台。
    ```

#### 4.4.4 回归用例

- 用例 R10：模拟 12 轮对话，验证第 12 轮仍能正确回答平台、赛道、人设。
- 用例 R11：长对话中用户说「给我生成图文版」，验证模型能回忆到最早的视频脚本主题。

### 阶段五：指代消解与意图补全（P1，第 5-6 周）

#### 4.5.1 目标
提升对「那么图文的又咋做」「接上一个问题」等省略表达的识别能力。

#### 4.5.2 任务清单

| 任务编号 | 任务 | 负责人 | 输出物 | 验收标准 |
|---|---|---|---|---|
| P1-7 | 在 system prompt 中增加指代消解提示 | LLM | prompt 模板 | 模型明确知道要结合上下文理解短消息 |
| P1-8 | 实现短消息意图补全逻辑 | 后端/LLM | 预处理函数 | 对长度 < 10 字或含「那么/接上/刚才」的消息，先补全为完整意图 |
| P1-9 | 对补全结果进行置信度判断 | 后端/LLM | 判断逻辑 | 置信度低时主动向用户确认，而不是胡说 |

#### 4.5.3 关键设计

- **system prompt 提示**：
  ```
  用户可能会使用省略表达或指代前文（如「那么图文的呢」「接上一个问题」）。
  请结合完整对话历史理解用户意图，不要当作新话题处理。
  如果你不确定用户指代的内容，请礼貌地确认，不要编造。
  ```

- **意图补全示例**：
  - 用户输入：「那么图文的又咋做」
  - 补全后：「用户希望基于上一轮生成的「视频号养生爆款脚本」主题，生成一份对应的图文内容。」
  - 如果补全置信度低，则回复：「你是想让我把刚才的养生视频脚本改成图文版本吗？」

#### 4.5.4 回归用例

- 用例 R12：复现第 29 条「那么图文的又咋做」，验证系统生成与第 28 条主题一致的图文内容。
- 用例 R13：复现第 21 条「接上一个问题，我要在视频号上发的」，验证系统能回忆起上一条主题是「运动类养生内容人设」。

### 阶段六：人设固化和可观测（P2，第 6-7 周）

#### 4.6.1 目标
统一 Lumina 的人设和回复风格，增强日志可观测性。

#### 4.6.2 任务清单

| 任务编号 | 任务 | 负责人 | 输出物 | 验收标准 |
|---|---|---|---|---|
| P2-1 | 固化 system prompt 人设 | 产品/LLM | prompt 文档 | 所有开场白使用统一名称和能力列表 |
| P2-2 | 开场白模板化 | 前端/LLM | 模板 | 避免每次回复风格不一致 |
| P2-3 | 日志增强字段 | 后端 | 日志 schema | 记录 session_round、context_hit、platform_source、tool_platform_aligned |
| P2-4 | 搭建监控看板 | 后端/数据 | 看板 | 监控平台一致率、上下文命中率、会话中断率 |
| P2-5 | 建立回归测试集 | 测试 | 测试用例 | 覆盖第 4、7、14、16、20、21、28→29 条等关键场景 |

#### 4.6.3 关键设计

- **system prompt 人设示例**：
  ```
  你是 Lumina，一个对话式 AI 营销智能助手，专注于帮助个人创作者和 KOL 进行内容营销。
  你的能力包括：生成文案（小红书/抖音/视频号/B站）、账号诊断、选题推荐、合规检测、流量分析。
  回复风格：简洁、实用、结构化，必要时使用表格和 emoji。
  ```

- **新增日志字段**：
  | 字段 | 含义 |
  |---|---|
  | `session_round` | 当前会话第几轮 |
  | `context_hit` | 是否命中上下文（历史拼接是否生效） |
  | `platform_source` | 平台来源：画像/当前消息/历史推断/LLM默认 |
  | `tool_platform_aligned` | 同一次请求内工具平台是否一致 |
  | `intent_completion` | 是否经过意图补全 |

## 六、验收标准

### 6.1 整体指标

| 指标 | 目标值 | 说明 |
|---|---|---|
| 平台一致率 | ≥ 90% | 用户已声明平台后，工具调用平台与声明一致的比例 |
| 上下文命中率 | ≥ 85% | 含「接上/那么/刚才」等词的请求，被正确承接的比例 |
| 会话中断率 | ≤ 5% | 非用户主动新建对话情况下，`conversation_id` 切换的比例 |
| 入口 conversation_id 丢失率 | ≤ 5% | 刷新页面或从任意入口重新进入后，`conversation_id` 丢失导致重新开场的比例 |
| 长对话稳定率 | ≥ 80% | 10 轮以上对话仍能回忆关键事实的比例 |

### 6.2 关键回归用例（对应日志中的问题记录）

| 用例编号 | 复现场景 | 通过标准 |
|---|---|---|
| R1 | 连续多轮对话 | `conversation_id` 一致，`history_len` 递增 |
| R2 | 刷新页面后继续对话 | `conversation_id` 不变 |
| R3 | 第 28→29 条：视频脚本 → 图文怎么做 | 系统承接视频脚本主题，生成图文内容 |
| R4 | 声明视频号后省略平台词 | 工具平台为视频号 |
| R5 | 第 14 条：「怎么打造养生账号 ip」 | 工具平台为视频号，不是小红书 |
| R6 | 第 7 条：一次请求内多工具 | 平台一致，不出现 xiaohongshu+douyin 混用 |
| R7 | 刷新页面或从任意入口重新进入 | `conversation_id` 与进入前一致，不重新开场 |
| R10 | 12 轮长对话 | 第 12 轮能正确回答平台、赛道、人设 |
| R12 | 第 29 条「那么图文的又咋做」 | 正确承接前文 |
| R13 | 第 21 条「接上一个问题」 | 正确回忆主题并生成视频号内容 |

## 七、风险与应对

| 风险 | 影响 | 应对措施 |
|---|---|---|
| 历史消息拼接后 prompt 过长，导致成本上升或响应变慢 | 性能/成本 | 配合阶段四的摘要机制，控制历史长度；可按 token 数动态截断 |
| 平台画像更新策略过严，用户切换平台时体验僵硬 | 体验 | 增加平台切换识别：用户明确说「我现在做小红书」时更新画像并提示 |
| 多平台对比需求被平台归一校验误伤 | 功能 | 校验逻辑中识别「对比」关键词，允许多平台调用 |
| 摘要生成不准确，丢失关键信息 | 体验 | 摘要生成后不回写删除原消息，原消息仍保留在存储中；摘要仅用于 prompt |
| 前端状态持久化方案不同端不一致 | 兼容性 | Web 用 localStorage，App 端用本地存储，服务端以 `conversation_id` 为准 |
| 改造范围跨前端/后端/LLM，协调成本高 | 进度 | 按阶段里程碑验收，每阶段完成后做集成测试 |
