## 五、问题 3：会话 ID / 请求 ID 每次都不同是否正确

### 5.1 请求 ID（request_id）每次不同：正常
- request_id 是单次 HTTP/API 请求的唯一标识，29 次请求 29 个不同 request_id 是正确设计。

### 5.2 会话 ID（conversation_id）每次不同：异常
- 正常多轮对话：一次完整的对话流由同一 `conversation_id` 串联，后端通过 `conversation_id` 查询历史消息。
- 本日志：29 条请求对应 29 个不同的 `conversation_id`，说明每次请求都被当作一次「新对话」。
- 这是测试员感觉「记不住用户信息」和「没有历史对话」的根本原因。

### 5.3 为什么不能仅靠 user_id 维系对话
- 同一用户可能同时打开多个会话（如多个浏览器标签、移动端和 Web 端）。
- 如果仅靠 user_id 查询最近一条消息作为上下文，会导致多个会话之间的消息互相串扰。
- 正确做法是：`conversation_id` 作为会话维度，`user_id` 作为用户权限与画像维度。

## 六、综合结论

1. **三个问题的共同根因是「会话管理失效」**：每次请求都使用新的 `conversation_id`，`history_len` 始终为 0，导致系统无法记住用户已声明的平台、无法理解前文、无法保持多轮对话。
2. **平台乱窜不是 LLM 理解能力差，而是上下文丢失**。当用户未在当前条消息中重复平台时，planner 默认按「小红书」推断；即使重复了，也可能因为工具参数生成逻辑没有约束而出错。
3. **「解决方案」入口感知为全新对话，是 conversation_id 未固定的直接表现**。当前端未复用 conversation_id 时，无论从输入框还是功能入口进入，系统都会按新会话处理。
4. **顶层 `platform` 字段未回填**。如果后端或前端能把这个字段正确填充并传给 planner，可以部分缓解平台乱窜问题，但无法解决连续性问题。

## 七、建议修复方向（供参考，不改动代码）

1. **会话复用机制**：确保同一用户的前后轮对话使用同一个 `conversation_id`，直到用户手动新建会话或会话超时。
2. **历史消息拼接**：后端根据 `conversation_id` 查询历史消息，并在请求时正确设置 `history_len`，将历史上下文拼入 LLM prompt。
3. **平台字段持久化**：将用户声明的平台写入会话上下文或用户画像，工具调用时优先读取上下文中的平台，而不是让 LLM 凭空推断。
4. **前端会话状态持久化**：前端在页面刷新、切换路由或从功能入口进入时，应从本地存储或服务端恢复当前 `conversation_id`，确保同一用户的连续请求落在同一个会话内。
5. **工具参数校验**：在 planner 生成工具参数时，增加「平台一致性」校验：如果上下文/平台字段已声明，则不得擅自切换为其他平台。
6. **日志增强**：建议记录「当前会话轮次」「是否命中上下文」「平台来源」等字段，便于后续排查类似问题。

## 八、补充：固定 conversation_id 后的再思考

> 注：用户反馈已实施「固定 conversation_id」的工程改造。由于日志仍为改造前数据，以下分析是在假设 conversation_id 已复用的前提下，对仍可能存在的风险与验证点的推演。

### 8.1 固定 conversation_id 能直接解决什么

1. **会话维度打通**：后端可以通过同一个 `conversation_id` 查询历史消息，为多轮对话提供基础。
2. **history_len 有机会大于 0**：只要后端把历史消息拼入 LLM prompt，`history_len` 就会随着轮次增长。
3. **第 29 条「那么图文的又咋做」有机会成功**：因为第 28 条的视频脚本主题在同一 conversation_id 下可见，模型可以正确指代「图文」对应的内容。
4. **从任何入口进入都不会被当作新对话**：只要前端把 `conversation_id` 带过来，无论用户从输入框、解决方案按钮还是刷新页面后进入，系统都能继续当前会话，不再重复开场白。

### 8.2 即使 conversation_id 固定，仍可能存在的残余风险

#### 8.2.1 history_len 仍然为 0（工程未真正拼接历史）

- **风险描述**：如果仅固定了 conversation_id，但后端或 planner 仍然只取当前一条消息，`history_len` 继续为 0，那么第 29 条仍会失败。
- **验证方法**：查看新日志中同一会话的第 2 轮、第 3 轮请求的 `history_len` 是否从 0 递增。
- **关键指标**：`history_len > 0` 且 `conversation_id` 相同。

#### 8.2.2 平台信息未持久化，仅靠 LLM 从历史中回忆

- **风险描述**：即使 LLM 能看到历史，平台信息仍分散在多轮消息中。当用户某条消息未明确写「视频号」时，模型仍可能按训练分布默认推断为「小红书」。
- **典型案例**：第 14 条「怎么打造养生账号 ip」、第 16 条「养生赛道，中老年，还没产出过内容」、第 20 条「运动类的养生内容人设，怎么写内容」——这些消息没有平台词，但上下文都在聊视频号。如果模型没有平台画像，仍可能调用 `xiaohongshu`。
- **建议**：将用户声明的平台写入会话级画像（或回填到顶层 `platform` 字段），工具调用时优先使用画像中的平台，而不是让 LLM 从历史中重新推断。

#### 8.2.3 同一次请求中工具平台不一致

- **风险描述**：第 7 条同时调用 `xiaohongshu` 和 `douyin` 两个平台。这说明 planner 对一次请求内的工具参数没有统一约束。
- **建议**：在一次用户请求中，所有工具的平台参数应默认一致（除非用户明确说「对比小红书/抖音」）。可在调用工具前增加一层「平台归一」校验。

#### 8.2.4 指代消解与省略恢复仍然依赖模型能力

- **风险描述**：第 29 条「那么图文的又咋做」、第 21 条「接上一个问题，我要在视频号上发的」都属于省略表达。即使 conversation_id 固定，模型是否能正确把「图文」对应到上一条视频脚本的主题，取决于历史消息的拼接方式和模型的理解能力。
- **建议**：在 prompt 中显式提示模型注意「当前请求可能包含对前文的指代，请结合上下文理解」；对特别短的省略消息，可增加一层「意图补全」逻辑。

#### 8.2.5 历史消息过长导致关键信息被淹没

- **风险描述**：测试员在 4 小时内产生了 29 条记录，如果全部拼入 prompt，上下文会非常长。LLM 可能会在大量历史消息中丢失「用户要做视频号养生 IP」这个关键事实。
- **建议**：引入会话摘要（conversation summary）机制，定期对长对话做摘要，并把关键信息（平台、赛道、人设、目标人群）提升到用户画像中。

#### 8.2.6 页面刷新/路由切换后 conversation_id 丢失

- **风险描述**：测试员说「从解决方案进入的体验，每个按钮都是全新页面」。本质上不是按钮本身的问题，而是 `conversation_id` 没有在前端持久化。刷新页面、切换路由或从任何入口重新进入时，前端如果生成新的 `conversation_id`，就会重新开场。
- **建议**：前端将 `conversation_id` 保存在 `localStorage`/`sessionStorage` 或客户端状态管理中，任何入口发送请求时都携带该 ID；会话新建策略由后端或用户主动「新建对话」按钮控制。

#### 8.2.7 人设/回复风格不一致

- **风险描述**：日志中多次「你好啊」的回复话术不一致（有的叫「对话式 AI 营销智能助手」，有的说「AI 营销助手」，有的列出能力不同）。即使历史拼接，如果没有系统级人设约束，长对话中风格也可能漂移。
- **建议**：在系统提示（system prompt）中固化人设、能力边界、开场白模板，避免完全由模型自由发挥。

### 8.3 改造后的验证清单

| 验证项 | 通过标准 | 优先级 |
